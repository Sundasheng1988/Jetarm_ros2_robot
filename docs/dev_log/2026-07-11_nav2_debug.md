## 根因分析

### 为什么不是 AMCL 的问题？

AMCL 的工作方式：

1. 接收 `odom_combined` 作为运动预测（里程计运动模型）。
2. 接收 `/scan` 作为观测（激光似然模型）。
3. 计算 `map → odom_combined` 的修正变换。

**理论关系：**

```
如果 odom 认为转了 132°，实际只转了 90°，
AMCL 应该输出 map → odom 补偿 -42°。
```

你在数据中确实看到 AMCL 在修正（`map → odom_combined` 从 41.587° 到 99.445°），但修正幅度异常大。这不是 AMCL 参数（alpha1–alpha4、update_min_a、laser_model）可以解决的 —— 无论 AMCL 参数怎么调，输入（odom）已经错了。

### 当前最大嫌疑：STM32 Odom 角速度链路

桥接代码中有一段历史修改：

```c
Robot_Vel.Z = Odom_Trans(rx[6], rx[7]) * 1.10;
```

**历史背景：** ×1.10 比例补偿是之前因角速度偏小临时添加的，当前需要重新验证该补偿是否仍然正确，不能直接假设比例补偿有效。

**三种可能原因，优先级从高到低：**

| 可能性 | 说明 | 判断方式 |
|------|------|------|
| **A. 单位错误** | STM32 发 deg/s，ROS 认为 rad/s（差 57.3 倍）| 看 angular.z 原始值大小 |
| **B. 轮速符号错误** | 左右轮速度相减符号反了，导致 `omega = (vr - vl) / wheel_base` 符号错误 | 旋转时 angular.z 方向与实际相反或乱跳 |
| **C. 编码器/电机方向不一致** | 编码器增量方向与电机实际转向不一致 | odom yaw 非单调变化（132 → 20）|
