## 1. 本次事件摘要

2026-08-12 的问题并不是 Rebecca 整套语音系统突然完全不可用。

本轮最初真正需要解决的是一个比较窄的导航交互问题：

> **当 Rebecca 正在播报“将前往餐厅，是否确认”时，用户立即说“取消”或“确认”，ASR 经常已经听见，但因为处于 TTS interrupt-only 模式，没有把控制词继续送给 Voice Agent，导致用户需要重复说几次。**

原始交互表现：

```text
Rebecca:
“将前往餐厅，是否确认？”

用户:
“取消”

ASR:
🎧(interrupt) -> '取消。' / 类似片段

但没有进入正常 /speech_query
→ Voice Agent 没收到
→ 用户感觉“取消没有反应”
→ 再说一次
→ TTS 结束后才成功
```

这个问题本身是局部的。

但 8/12 后续为了修复它，修改范围逐渐扩大到了：

- `speech_dialog_funasr_node.py`
- `tts_speaker_node.py`
- `llm_voice_agent_node.py`
- TTS speaking lifecycle
- self-echo timing
- interrupt 语义
- 控制词直通
- navigation confirmation
- shared task confirmation

最终导致原本已经较稳定的 Rebecca 语音体验发生明显回归，包括：

- self-echo 增强；
- Rebecca 更容易听见自己的尾音；
- System Sleep / Wake 体验变差；
- 对话节奏变得不稳定；
- 原本已经工作较好的语音行为被覆盖/回退；
- 新导航逻辑与旧语音稳定逻辑混在一起修改，定位困难。

本日最重要的结论：

> **问题不在于“导航功能本身设计错了”，而在于一次局部交互问题修复扩大成了跨层行为修改，没有先锁定稳定基线，也没有把 ASR、TTS、Agent 三层职责严格隔离。**

## 3. 原始问题：为什么“取消”经常要说几遍

### 3.1 当前 ASR 的双模式设计

`speech_dialog_funasr_node.py` 实际存在两种语音处理状态。

#### 正常 ASR 模式

```text
用户说话
→ endpoint
→ 文本过滤
→ /speech_query
```

在正常模式下，已经增加了 `CONTROL_REPLIES`：

```python
CONTROL_REPLIES = {
    '确认',
    '确定',
    '执行',
    '好的',
    '好',
    '行',
    'ok',
    '可以',
    '是的',
    '没问题',

    '取消',
    '不去',
    '不要',
    '别去',
    '先不要',
    '算了',
    '不用',
    '停止',
}
```

作用：

```text
“确认”
“取消”
```

虽然字符很短，也不会再被：

```python
min_text_len = 4
```

过滤掉。

因此在 TTS 已经结束时：

```text
用户：取消
→ 🎧 endpoint
→ 🎛️ 控制短语直通
→ /speech_query
→ Voice Agent
→ nav_cancel
```

这条链是正常的。

### 3.2 TTS 播放期间进入 interrupt-only

为了防止 Rebecca 自己听见自己的扬声器声音，TTS 播放期间 ASR 不走正常 endpoint 路径，而进入：

```text
interrupt-only
```

此时目标原本是：

```text
Rebecca 正在讲话
→ 麦克风仍然监听
→ 只识别“停一下 / 别说了 / 停止说话”等真正的打断
→ 其他内容不向 /speech_query 发布
```

这是正确的总体方向。

问题在于：

```text
确认
取消
停止导航
取消导航
```

本质上既不是普通聊天，也不只是“停止播报”。

它们是：

> **机器人状态机控制输入。**

尤其是：

```text
取消
停止导航
停止移动
```

属于安全优先级更高的控制命令。

### 3.3 日志已经证明：ASR 听见了，但没有继续传

典型现象：

```text
🎧(interrupt) -> '确认。' (conf~1.00) hit=False
```

这意味着：

```text
麦克风听见了
FunASR 识别出来了
但 interrupt-only 判断 hit=False
所以没有发布 /speech_query
```

因此不是：

```text
Voice Agent 不会取消
```

而是：

```text
Voice Agent 根本没有收到“取消”
```

这就是“经常需要说几遍”的直接原因。

## 5. 本次发现的关键代码回归

### 5.1 `tts_speaker_node.py`

本地审计发现：

```text
CURRENT == Git HEAD
```

而 Git HEAD 实际是：

```text
2026-08-08 的稳定里程碑
```

不是 8/10～8/11 最终工作状态。

期间曾存在一版未提交的 TTS 改进逻辑，包括：

```python
self._audio_playing
self._audio_state_lock
_set_audio_playing()
```

其设计语义是：

```text
_speaking
= TTS session / queue 正在工作

_audio_playing
= 扬声器此刻真正出声
```

并让：

```text
/tts_speaking=True
```

严格跟随真实播放器生命周期。

后续该版本没有 commit，当前代码又回到了更老的 HEAD。

这说明：

> **仅仅看 Git diff 不足以判断是否发生回归，因为未提交的稳定改进可能已经被覆盖。**

### 5.2 `speech_dialog_funasr_node.py`

该文件在 8/12 被多次修改。

历史版本里存在更完整的 self-echo 防护，例如：

```python
if speaking:
    self.last_tts_time = now
```

以及：

```python
_is_recent_tts_echo()
_norm_control_text()
```

后续部分逻辑被删除、内联或改写。

核心风险是：

```text
Agent 产生 /speech_reply
→ last_tts_time 计时开始
→ CosyVoice 还要合成
→ 真正播放更晚
```

如果 self-echo 窗口以文本产生时间为锚，而不是实际播放时间，就容易出现：

```text
TTS 播放尾音
→ self_speech_window 已接近过期
→ Rebecca 自己的尾音泄漏成正常 endpoint
→ /speech_query
```

这和 8/12 观察到的 self-echo 回归一致。

### 5.3 `llm_voice_agent_node.py`

该文件新增了大量导航逻辑，包括：

```text
NAV_STOP_PHRASES
_pending_nav
_handle_navigation()
is_nav_confirm_reply()
is_nav_cancel_reply()
is_stop_movement()
extract_navigation_place()
```

这些导航逻辑整体应该保留。

但是开发过程中也修改了 shared task confirmation：

```text
_handle_task()
```

把原来相对宽松的：

```text
CONFIRM_WORDS / CANCEL_WORDS substring matching
```

改成了更严格的 navigation-style confirm/cancel helper。

这导致一些机械臂任务确认表达：

```text
我确认
确认一下
可以执行
```

可能不再和以前一样工作。

说明：

> **导航确认和机械臂任务确认虽然都叫“确认”，但不应该默认共享完全相同的 matcher。**

## 6. 为什么 System Sleep 一度看起来也坏了

后续审计发现：

```text
SYSTEM_SLEEP_KEYWORDS
SYSTEM_WAKE_KEYWORDS
system_active
```

本身并没有明确的代码回退证据。

真正的 System Sleep 命令要求完整匹配：

```text
瑞贝卡系统休眠
```

而不是：

```text
系统休眠
```

8/12 一度出现：

```text
系统休眠
→ GLM 回答“好的，系统已休眠”
```

但系统状态实际上没有进入 inactive。

这属于：

> **LLM 的语言回复和真实 robot state 不一致。**

恢复后再次实测：

```text
瑞贝卡系统休眠
```

日志明确出现：

```text
🌙 L2 SYSTEM_SLEEP triggered
🌙 L2 SYSTEM_SLEEP (active → inactive)
```

之后普通问题不再得到 Agent 回复。

再说：

```text
瑞贝卡启动系统
```

日志出现：

```text
🌅 L2 SYSTEM_WAKE (boot → active)
```

说明 System Sleep / Wake 本体是工作的。

本轮经验：

> **涉及机器人状态的动作，不能以 TTS/LLM 说了什么作为成功判断，必须检查 state transition 或执行结果。**

## 10. 下一轮修改必须遵守的原则

### Rule 1 — 一次只改一个问题

下一轮目标只能是：

> **TTS 正在播放时，让明确的导航取消/停止命令可靠穿透 interrupt-only。**

不要同时优化：

- hotword；
- confidence；
- TTS lifecycle；
- wake window；
- sleep；
- chat；
- navigation parser；
- task confirm。

### Rule 2 — 优先只改 `speech_dialog_funasr_node.py`

下一轮第一选择：

```text
只改：
speech_dialog_funasr_node.py

不改：
tts_speaker_node.py
llm_voice_agent_node.py
```

因为当前证据表明：

```text
Voice Agent cancel state machine 已经有效
```

问题主要发生在：

```text
ASR → Agent
```

之间。

### Rule 3 — 不允许把“取消”简单加入 interrupt_words

不能简单：

```python
interrupt_words += ['取消']
```

原因：

Rebecca 自己可能播报：

```text
“请说确认开始导航，或取消放弃。”
```

麦克风可能识别自己的：

```text
取消
```

从而出现：

```text
Rebecca 自己说取消
→ ASR hit=True
→ 自己取消导航
```

这是不可接受的。

### Rule 4 — interrupt-only 中必须先 self-echo，再 control passthrough

推荐顺序：

```text
TTS playing
↓
ASR 得到文本
↓
1. 判断是不是近期 TTS self-echo
   YES → 丢弃
↓
2. 判断是不是明确的高优先级 robot cancel/stop
   YES →
       interrupt TTS
       +
       发布 /speech_query
       return
↓
3. 普通 TTS interrupt words
   “停一下 / 别说了 / 闭嘴”
↓
4. 其他内容丢弃
```

安全控制词建议优先支持：

```text
取消导航
停止导航
停止移动
取消移动
别走了
不要走了
停下导航
停下移动
```

对于单独：

```text
取消
```

只建议在：

```text
Voice Agent 当前明确处于 nav_wait_confirm
```

的上下文中允许穿透。

如果 ASR 层拿不到该状态，则需要非常谨慎，不应仅凭词本身全局放行。

### Rule 5 — “确认”和“取消”不能完全对称处理

取消属于安全侧命令：

```text
有疑问时宁可停止
```

确认属于执行侧命令：

```text
有疑问时不能启动机器人
```

因此设计原则应该是：

```text
取消：更容易穿透
确认：更严格
```

即：

```text
False Positive Cancel
通常只会让机器人停止/不执行

False Positive Confirm
可能直接启动实体机器人
```

二者风险完全不同。

### Rule 6 — TTS interrupt 和 robot navigation cancel 必须严格分离

```text
“别说了”
= 停止 Rebecca 播报

“停止移动”
= 停止机器人导航
```

不能共享同一个最终语义。

推荐保持：

```text
/tts/interrupt
→ audio control

/voice_input/input: 停止移动
→ robot navigation control
```

两者可以由同一句用户语音同时触发，但下游职责不能混在一起。

例如：

```text
用户：
“停止导航”

ASR:
→ /tts/interrupt = true
→ /speech_query = 停止导航

Agent:
→ /voice_input/input = 停止移动
```

### Rule 7 — 不要因为减少启动命令而合并 package

当前：

```text
navigation_intent
→ llm_parser

navigation_executor_node
→ place_manager

rebecca_voice_start
→ llm_voice_agent
```

职责分离本身合理。

如果未来希望一条命令启动：

```text
Voice + Parser + Navigation Executor
```

应该增加：

```text
top-level orchestration launch
```

而不是因为“节点多”就移动源码或合并 package。

### Rule 8 — 每轮修改前必须有 Git checkpoint

以后任何语音核心修改前：

```bash
git status
git diff
git log -1 --oneline
```

如果当前状态已经实测稳定：

```text
先 commit
先 tag
再修改
```

禁止再次出现：

```text
“这版很好用，但没有 commit”
```

的情况。

### Rule 9 — 不允许大范围 restore

以后禁止为了恢复语音行为直接：

```bash
git restore <whole-file>
git checkout -- <whole-file>
git reset --hard
```

特别是在 feature branch 有大量 uncommitted work 时。

优先：

```text
read-only diff
→ hunk classification
→ minimal patch
```

### Rule 10 — 测试必须分层

每次修改按以下顺序。

#### Layer A — Voice only

验证：

```text
wake
chat
sleep
wake-from-sleep
TTS
self-echo
interrupt
```

#### Layer B — Voice Agent navigation only

Parser/Nav2 不启动。

验证：

```text
瑞贝卡去餐厅
→ pending

确认
→ /voice_input/input = 导航到餐厅

取消
→ 不应下发导航
```

#### Layer C — Parser

验证：

```text
/voice_input/input
→ /parsed_command
```

#### Layer D — Navigation Executor / Place Manager

验证：

```text
parsed_command
→ /goto_place
```

#### Layer E — Real Nav2

最后才允许实体机器人移动。

绝对不要一边调 ASR/TTS，一边直接用真实 Nav2 判断语音是否正确。

## 13. 本次最重要的工程结论

本次问题最大的教训不是某一行代码写错。

而是：

> **在已经接近可用的机器人系统里，一个局部交互 bug 不应该通过跨 ASR、TTS、Agent、Navigation 多层重构来修。**

Rebecca 当前已经不是一个单节点 demo，而是一个多状态、多执行器的机器人语音系统：

```text
ASR
→ attention state
→ LLM / deterministic intent
→ confirmation state
→ parser
→ executor
→ physical robot
→ execution result
→ TTS
→ microphone again
```

这里任何一个“看起来只是语音的小改动”，实际上都可能改变整个闭环时间语义。

因此后续开发必须坚持：

```text
稳定基线
→ 单问题
→ 单层定位
→ 最小 patch
→ 分层测试
→ commit/tag
→ 再继续
```

而不是：

```text
发现一个问题
→ 同时改多个节点
→ 行为互相影响
→ 再继续补丁
→ 最后无法判断哪一版最好
```
